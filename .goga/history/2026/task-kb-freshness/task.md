# Свежесть KB: автообнаружение патчей игры + обновление данных без релиза

## Current State

aoe2-lsp v0.4.x: KB зашита в бинарник (`internal/kb/data/*.json`, embed) —
каждый патч AoE2 DE требует ручного пересбора источников, регенерации KB
и **релиза сервера**, чтобы пользователи увидели новые команды/функции.
Обнаружение патчей тоже ручное: `docs/ref/aoe2de-xs-rms-changelog.md`
собран 2026-09-04 просмотром 77 постов ageofempires.com/news руками.
Процесс обновления KB документируется в #57 (kb-refresh), но триггера
«появился патч» нет вовсе, а канала доставки данных без релиза — тоже.

## Description

Бэклог-пачка из 2 слотов, замыкающая цикл свежести KB: слот A
автоматизирует **обнаружение** новых патчей игры (scheduled workflow →
issue-триггер), слот B проектирует **доставку** обновлённых данных в
сервер без пересборки бинарника. Каждый слот берётся отдельно, в ветке
`task/<имя-слота>` → PR. Не зависит от эпика v1.0.0.

## Scope

**In scope (слоты):**

| Слот | Что делаем | Ячейки/области | Размер |
|---|---|---|---|
| `release-notes-monitor` | Scheduled workflow: раз в день проверяет ageofempires.com/news на новые посты Update/Minor Update/Hotfix AoE2 DE; детектор — Go-инструмент (cmd/ + internal/, stdlib: `net/http`, `encoding/xml` для RSS-фида, regexp-фолбэк по HTML); новый пост → `gh issue create` по шаблону (ссылка, дата, чеклист kb-refresh); state — файл в репо с последним обработанным постом (workflow коммитит обратно), дедуп дополнительно по открытым issue с меткой `kb-refresh` | .github/workflows, новый тонкий cmd + ячейка детектора, CI | S–M |
| `kb-live-update` | Design-only: `docs/design/kb-live-update.md` с ADR-разделом. Вопросы: внешний источник данных vs embed-фолбэк (флаг/переменная окружения с путём к JSON), версионирование данных против схемы `Store` (проверка совместимости), канал публикации данных (data-only asset в Releases / отдельная ветка / другое), связь с процессом kb-refresh (#57) и monitor-воркфлоу из слота A. Код не пишем; реализация — отдельная задача по ADR, кандидат 1.x | docs/design, (при реализации: kb, server, cmd/aoe2-lsp) | S–M |

**Out of scope:**

- автопарсинг XS/RMS-изменений из поста и автогенерация KB — остаётся
  ручным процессом по #57 (issue из слота A только триггерит его)
- обновление UGC Guide / Zetnus-источников (внешние мейнтейнеры) —
  тоже #57
- доставка бинарника сервера пользователям (#52, #49) и version-check
  в самом сервере — смежные, но отдельные вопросы
- реализация механизма из ADR слота B (кандидат 1.x)

## Acceptance Criteria

Общие для каждого слота:

- `make check` зелёный; `goga contract` затронутых ячеек зелёный

Слотовые критерии:

- `release-notes-monitor`: прогон `workflow_dispatch` на актуальном
  состоянии не создаёт issue и не меняет state; симуляция нового поста
  (временная подмена state на более старый пост) создаёт ровно один
  issue по шаблону и обновляет state; детектор покрыт тестами (фикстуры
  фида/HTML в testdata); воркфлоу падает loudly (non-zero exit), если
  источник не удалось распарсить — тихая деградация запрещена
- `kb-live-update`: ADR фиксирует выбранный механизм, отвергнутые
  альтернативы и критерии выбора; офлайн-запуск сервера без внешних
  данных остаётся рабочим (embed-фолбэк обязателен); реализация
  оформлена отдельной задачей-кандидатом 1.x

## Stack

- **Frameworks:** Go 1.26+ (stdlib: `net/http`, `encoding/xml`,
  `regexp`) для детектора
- **Libraries:** без новых зависимостей
- **Infrastructure:** GitHub Actions (schedule + workflow_dispatch,
  permissions `contents: write` + `issues: write`), `gh` CLI из коробки

| ageofempires.com/news (RSS/HTML) | — | внешний источник, уже используется вручную; usage не требуется |

## Risks and Constraints

- ageofempires.com может менять вёрстку или не иметь RSS — детектор
  обязан падать явно, а не молча пропускать патчи; это главный
  принимаемый риск
- серия hotfix'ов за один прогон — создавать один issue на батч постов
  (не по issue на пост)
- cron-триггеры не работают в форках — норм для upstream
- `kb-live-update`: выбранный механизм не должен ломать офлайн-режим и
  не должен требовать от пользователя ручных действий сверх установки
  сервера

## Scope Estimate

2 слота (S–M + S–M design), каждый — независимая задача со своей веткой
и PR; зеркало — отдельные GitHub issues.

## Existing Architecture

- `release-notes-monitor` — новый тонкий entrypoint в `cmd/` + ячейка
  детектора под `internal/` (по образцу kbgen); воркфлоу по паттернам
  cook `github-actions.md`; state-файльчик рядом с
  `docs/ref/aoe2de-xs-rms-changelog.md`
- `kb-live-update` — опирается на `kb.Store`/`NewStore` (сегодня только
  embed), `server.Serve` (прокидывание пути к данным), пайплайн
  `kb.GenKB` (кандидат на выпуск обновлённых данных)
