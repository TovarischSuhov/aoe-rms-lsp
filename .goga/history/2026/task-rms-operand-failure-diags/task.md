# rms-operand-failure-diags: каждый провал парса операнда получает диагностику

## Current State

`format.RMS` (`internal/format`, rms.go:32) отказывается от форматирования
только при error-severity диагностиках `Parse` (шаг 1 её алгоритма). Парсер
`internal/rms` на путях провала парса операндов сегодня молчит — байты
исчезают из конвейера без AST-представления и без Diagnostic, поэтому
форматтер не отказывается и печатает потерю.

Воспроизводитель из issue #96 (HEAD 2026-10-05, master 101a7b0):

```
end_random. ('150% (
```

парсится без единой error-диагностики; zero-width аргументы печатаются
пустотой, репарс даёт другую арность (`args=2` → `args=1`) — INV1
`parse(format(x)) ≡ parse(x)` нарушен на входе, который контракт обещал
форматировать. Печатная сторона защищена харденингом #45 (childless unary
перепечатывает байты оператора) — лечить надо парсер, как и сказано в issue.

Инвентарь путей молчаливой потери в выраженческом контуре
(внутренние функции parse.go, номера по HEAD 101a7b0):

| # | Место | Что молча теряется |
|---|-------|--------------------|
| 1 | `parseExpr`, binary-цикл (parse.go:1423-1428) | оператор потреблён, rhs провалился → возвращается lhs; оператор и rhs-байты исчезают |
| 2 | `parsePrimary`, ветка tokOp (parse.go:1469-1472) | childless unary с ok=true: аргумент печатается пустотой, арность меняется |
| 3 | `parsePrimary`, ветка tokLParen (parse.go:1481) | игнор ok от `parseExpr` → zero-width `Expr{}` в Args/Children |
| 4 | `parseCall` (parse.go:1513) | неожиданный токен внутри `f(...)` пропускается без диагностики |
| 5 | `parseCall` (parse.go:1509-1511) | незакрытая `(` при EOF: вызов полон в AST, но синтакс-ошибка без диагностики |
| 6 | `expressions` (parse.go:1326-1328) | `break` при провале `parseExpr`: остаток токен-рана строки не разбирается и не диагностируется |

Диагностируется только `tokUnknown` в `expressions` (error,
parse.go:1317-1322). Аннотации `Parse` (CODEMANIFEST rms) обещают «every
problem becomes a Diagnostic» — эти шесть путей исключения из собственного
контракта ячейки.

## Description

Критерий аудита: **каждый потреблённый токен либо представлен в AST, либо
покрыт Diagnostic**. Все шесть путей из инвентаря закрываются
диагностиками; новые провалы в этот критерий больше не попадают молча.

Политика severity:

- байты потеряны / арность искажена (№1–4, №6) → **error** — форматтер
  откажет через существующий шаг 1;
- конструкция полна в AST, но не завершена (№5, незакрытая `(` в вызове) →
  **warning**, по аналогии с существующим unclosed `{` (`syncOwner`,
  parse.go:672-684).

Точные тексты сообщений и привязка диапазонов (токен оператора для №2,
парность для №3/№5 и т.д.) — решение этапа плана.

Реализационно: `parseExpr`/`parsePrimary`/`parseCall` — свободные функции
без доступа к `parser.reportf`; потребуется протяжка diags-sink внутрь.
Ячейка `internal/format` не трогается — отказ воспроизводителя придёт сам.

## Scope

**In scope:**

- `internal/rms/parse.go`: диагностики на всех шести путях инвентаря по
  audit-критерию; протяжка diags-sink в `parseExpr`/`parsePrimary`/
  `parseCall`
- table-driven тесты в `internal/rms`: кейс на каждый путь (патологический
  вход → ожидаемые severity и диапазон) + регрессия «чистые входы не
  получают новых диагностик»
- тест в `internal/format`: отказ (sentinel, `errors.Is`) на
  воспроизводителе `end_random. ('150% (`
- CODEMANIFEST `internal/rms` тем же PR: audit-критерий фиксируется в
  Requirements `Parse` (шаг 6 алгоритма) — это сужение контракта, а не
  только код

**Out of scope:**

- #94 (интерливинг if-цепочек через секции), #95 (#-строка в скобках —
  реклассификация при репарсе), #135 (асимметрия mergeComments)
- публичная поверхность `Parse` (сигнатура) и формы AST: childless unary
  остаётся recovery-формой (принтер её переживает)
- принтер `internal/format` — харденинг #45 остаётся как defense-in-depth
- recovery вне выраженческого контура: brace-склейка, секционный sync,
  классификация директив
- правки потребителей diags (`server`/`analysis`/`hints`/`complete`/
  `include`) — для них изменение «просто больше error-диагностик»

## Acceptance Criteria

- каждый из шести путей даёт Diagnostic заявленной severity (№1–4, №6 —
  error; №5 — warning), диапазон покрывает потерянный/сломанный регион
- `end_random. ('150% (` → error-диагностика из `Parse`;
  `format.RMS` → err (sentinel, `errors.Is`), `formatted` пуст
- корпус 78 файлов: `TestRMS_Invariants` зелёные, новых knownDivergent нет
- чистые входы без новых диагностик: существующие тесты `rms`/`format`/
  `server` зелёные без правок ожиданий (кроме новых кейсов)
- `make check` зелёный; `goga contract internal/rms` зелёный; CI ветки
  зелёный

## Risks and Constraints

- рекурсия `parseExpr` (unary/paren/call): один провал всплывает через
  несколько уровней — риск дублей диагностик; в плане решить, кто эмитит
  (место провала — одно, внешние уровни не повторяют)
- тонкая регрессия: новая error-диагностика на валидном RMS мигрирует в
  отказ форматтера — канарейка корпус 78 файлов + существующие тесты
- №5 (warning) не меняет поведение форматтера — ценность чисто
  диагностическая; допустимо скоупить при необходимости, критерий аудита
  не страдает
- `expressions` вызывается и для значений атрибутов (путь past first value)
  — новые диагностики не должны ломать rename-индекс (`recordValueWords`);
  прогон `rename_test` обязателен
- готча: lint-хук блочит коммиты молча; тесты гонять под memory cap
