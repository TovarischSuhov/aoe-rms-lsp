  `EnclosingRanges` и `ReferencesAt`/`RenameSites` (`ast.go:246`, `666`).
- Прецедент RMS (#45, коммиты `59756db`→`ce6d07c`): `RmsFile.Comments
  []common.Range` — точные экстенты (блок от `/*` до `*/`, строчный до конца
  строки), сортировка по позиции, непересечение, тексты не хранятся
  (потребитель читает источник по `Offset`); контракт —
  `internal/rms/CODEMANIFEST:132`, тесты — `internal/rms/comments_test.go`.
  У XS аналога нет.
- Потребитель — будущий XS-принтер (#120, слот 3): печать `.xs` требует
  якорения комментариев по экстентам, как это уже делает RMS-принтер
  (`internal/format/rms.go:419-533` — список `comments` + индекс `pending`,
  `flushBefore`/`dropBefore`).
- Черновая разведка потерь AST (проверена по коду, уточняется аудитом):
  - модификаторы `rule` (`inactive`, `min-interval N`) проглатываются
    (`parse.go:260-262`) — в AST их нет, при этом `Decl.Range` их покрывает;
  - голый блок как выражение → `Expr{Kind: literal, Value: "{}"}`, `Range` —
    только открывающая `{`, тело блока в диапазон не входит (`parse.go:1013`);

    выражение, `Range` скобки не покрывает (`parse.go:1032-1036`);
  - лексерные: `1e5` сканируется как число `1` + идентификатор `e5`, `1.` —
    как число `1` + оператор `.` (`scanNumber`, `parse.go:1536+`);
  - тексты литералов при этом сохраняются дословно (`Expr.Value = tok.text`,
    `parse.go:1000`) — int/float/hex и escape-последовательности не теряются.

## Description

Экспорт XS-комментариев и сплошной аудит AST как вход для дизайна XS-принтера
(#120).

1. Разделить `xscanner.noncode` на два потока: комментарии (`//`, `/* */`) и
   строковые токены. Комментарии — экспортируемое `XsFile.Comments
   []common.Range` с гарантиями RMS-прецедента; строки остаются внутренними и
   продолжают питать «тишину» `CallAt`/`VisibleAt`/`EnclosingRanges`.
2. Записать `Comments` в `internal/xs/CODEMANIFEST` (модификация публичной
   поверхности — через goga-change flow, не read-only правка).
3. Аудит: сплошной обход видов деклараций (function/variable/rule/event/
   include/extern), стейтментов (все `Stmt*`) и выражений (все `Expr*`) плюс
   лексерных решений — что узел теряет относительно исходного текста: годится
   ли он для дословной печати и что принтеру придётся синтезировать. Находки —
   разделом `## Результаты` в этот же task.md.

Целевой вызов (якорь для #120; имена не фиксируются):

```go
file, _ := xs.XsParse(src, "a.xs")
for _, r := range file.Comments {
	text := src[r.Start.Offset:r.End.Offset] // тексты в AST не хранятся
}
```

## Risks and Constraints

- «Тишина» сейчас опирается на один поток `noncode`: после разделения
  `CallAt`/`VisibleAt` обязаны видеть оба (комментарии + строки), иначе
  позиция внутри строки начнёт отвечать как код — регресс навигации.
  Страховка — существующие тесты `navigation_test.go` (случаи in-string и
  in-comment).
- Экспорт строк в `Comments` недопустим: принтер заякорит строковый литерал
  как комментарий и напечатает его дважды.
- `XsParse` вызывается и на inline-XS из RMS-блоков: позиции и `Offset`
  относительны строки блока, а не файла RMS. Печатается inline-XS вербатим
  (решение сессии #45), поэтому конфликта нет — но ограничение фиксируется в
  контракте.
- Аудит без правок: находки могут потребовать изменения AST в #120 —
  объём той задачи оценивается отдельно, здесь ничего не «закладывается».
- Тесты — только под memory cap (`go test` в cgroup-песочнице, см. CLAUDE.md).

## Результаты (25.09.2026)

Сплошной аудит потерь XS AST — вход для дизайна XS-принтера (#120). Обход по
видам: `Decl` (`ast.go:12-25`), `Stmt` (`ast.go:37-66`), `Expr` (`ast.go:69-82`)
и лексерные решения (`internal/xs/parse.go`). Тон описательный: находки
фиксируют потери как есть; решения об изменениях AST/парсера — предмет #120,
здесь только фиксация. Колонка «что теряется» — то, что узел не сохраняет
относительно исходного текста; «годится ли для дословной печати» — можно ли
воспроизвести текст узла по одному AST; «что принтеру синтезировать» — текст,
которого в AST нет. Ссылки даны на `internal/xs` (`parse.go`, `ast.go`).

### Decl — 6 видов

| вид | что теряется | годится ли для дословной печати | что принтеру синтезировать |
|-----|--------------|---------------------------------|----------------------------|
| `function` (`DeclFunction`, `ast.go:14`) | `Range` кончается на конце последнего стейтмента тела либо на имени при теле `{}` (`parse.go:120`, `parse.go:125`, `parse.go:1279-1290`) — закрывающие `}` и, при пустом теле, `()`/`{}` вне `Range`; слова типа склеены одним пробелом (`parse.go:326`); значения параметров по умолчанию разбираются и отбрасываются (`parse.go:367-369`); `Body` хранит только стейтменты | сигнатура и тело — да; хвост `}` в `Range` отсутствует | `}` (и `()`, `{}` при пустом теле), скобки/запятые списка параметров, пробелы между словами типа |
| `variable` (`DeclVariable`, `ast.go:16`) | при списке `int a, b;` первый `Decl` имеет `Range` от типа до конца своего имени/инициализатора, запятая и следующий декларатор в него не входят (`parse.go:140-159`); каждый следующий декларатор начинается с собственного имени, слова типа в его `Range` не входят, хотя `Type` продублирован строкой (`parse.go:165`); `;` удлиняет `Range` только последнего декларатора (`parse.go:159`); инициализатор — синтетический `Stmt` (`initStmt`, `parse.go:216-227`) с дублированием имени в `ExprIdent` | имя, значение и `Type` — да; для деклараторов после первого слов типа в срезе `Range` нет | `,`, слова типа для деклараторов после первого, `;`, пробелы; имя декларатора не повторять (оно и в `Decl.Name`, и в `ExprIdent`) |
| `rule` (`DeclRule`, `ast.go:18`) | модификаторы между именем и телом (`inactive`, `min-interval N`) пропускаются циклом (`parse.go:262-264`) и в AST отсутствуют, при этом `Range` их покрывает; `Range` кончается концом последнего стейтмента тела, `}` вне него (`parse.go:268`, `parse.go:1279-1290`); при теле `{}` `Range` кончается на имени | имя и тело — да; модификаторы по AST не воспроизводимы | `{`/`}`, пробелы; модификаторы синтезируются только из исходника между именем и `{` |
| `event` (`DeclEvent`, `ast.go:20`) | аргументы `event(...)` разбираются, но в узле не сохраняются: `Name` — первый идентификатор среди аргументов (`parse.go:283`, `eventArgsName` `parse.go:303-311`), при аргументе-присваивании или строке `Name` пуст; `Range.End` — конец последнего аргумента (`parse.go:286`) | нет — список аргументов в узле отсутствует | содержимое `(...)` (кроме одного имени) из AST не восстановимо |
| `include` (`DeclInclude`, `ast.go:22`) | внешние кавычки пути снимаются (`strings.Trim(path.text, "\"")`, `parse.go:238`); формы `include` и `includeDuno` сводятся к одному `Kind` (`parse.go:71`, `parse.go:231`); при пути-идентификаторе текст хранится без изменений (`parse.go:240`) | имя и `;` — да; кавычек в `Name` нет | кавычки вокруг пути, пробелы; выбор написания `include`/`includeDuno` по AST не различим |
| `extern` (`DeclExtern`, `ast.go:24`) | `Type` — склейка слов типа одним пробелом (`parse.go:326`); при инициализаторе `extern int x = 1;` значение хранится синтетическим `initStmt` с дублированием имени (`parse.go:205`, `parse.go:216-227`); параметры хранятся без значений по умолчанию (`parse.go:367-369`); сигнатурная форма без `=` получает `Range.End` на `;` (`parse.go:210`) | имя, тип и параметры — да, дословные пробелы типа — нет | пробелы между словами типа, скобки/запятые списка параметров, `;` |

Сквозное по `Decl`:

- пустой `;` на верхнем уровне не порождает узла (`parse.go:55-59`);
  нераспознанный токен верхнего уровня даёт диагностику, токены пропускаются
  (`parse.go:62-65`, `parse.go:83-84`) — эти участки текста в AST отсутствуют;
- `Type` у всех видов с типом — `strings.Join(words, " ")` (`parse.go:326`),
  дословные пробелы между словами типа не сохранены.

### Stmt — 14 видов

| вид | что теряется | годится ли для дословной печати | что принтеру синтезировать |
|-----|--------------|---------------------------------|----------------------------|
| `block` (`StmtBlock`, `ast.go:39`) | `}` потребляется `parseBlock` (`parse.go:393`) и не входит ни в один `Range` (`blockEnd` только максимизирует концы стейтментов, `parse.go:1279-1290`); `Range` идёт от `{` до конца последнего стейтмента (`parse.go:405`); при пустом теле `Range` нулевой ширины на `{` | содержимое — да, закрывающая `}` — нет | `}`, пробелы и переводы строк |
| `if` (`StmtIf`, `ast.go:41`) | ветвь `else` не помечена отдельным полем: её наличие выводится из длины `Body` (`parse.go:500-507`); `else if` даёт `Body[1].Kind=StmtIf`, `else { if }` — `StmtBlock`; скобки условия в узле не представлены; при ветви-блоке её `}` вне `Range` | then/else восстановимы, ключевые слова — по `Kind` | `(`, `)`, `else`, `{`, `}` |
| `while` (`StmtWhile`, `ast.go:43`) | тело всегда ровно один стейтмент (`parse.go:528`); пустое тело `while (c) ;` даёт тело-`StmtExpr` без выражений (`parse.go:408-412`); `Range.End` = конец тела (`parse.go:529`) | да | `(`, `)`, пробелы; `;` пустого тела — из тела |
| `do` (`StmtDo`, `ast.go:45`) | `while`-клаузула и `;` синтезированы разбором, при отсутствии `while` это в узле не отражено (`parse.go:542-557`); условие — `Exprs[0]`; `Range.End` = конец `;` (`parse.go:557`) | при наличии условия — да | `do`, `while`, `(`, `)`, `;` |

| `switch` (`StmtSwitch`, `ast.go:49`) | `{`/`}` не входят в `Range` (`parse.go:723-727`); стейтменты до первого `case` попадают в тот же `Body`, что и ветви `case`, без пометки (`parse.go:715-716`) | subject и ветви — да | `switch`, `(`, `)`, `{`, `}` |
| `case` (`StmtCase`, `ast.go:51`) | ключевое слово `case`/`default` не хранится: `default:` и `case` с неразобранной меткой дают `StmtCase` с пустым `Exprs` и неразличимы (`parse.go:737-742`); `:` потребляется и не представлен (`parse.go:744`); `Body` — стейтменты до следующего `case`/`}` | метка — да, `default` — нет | `case`/`default`, `:`, `{`/`}` |
| `return` (`StmtReturn`, `ast.go:53`) | наличие значения выводится из длины `Exprs` (`parse.go:771-778`); `;` входит в `Range` через `expectSemi` (`parse.go:778`) | да | `return`, `;`, пробелы |
| `break` (`StmtBreak`, `ast.go:55`) | потерь нет: вид различает `break`, `Range` покрывает `break` и `;` (`parse.go:449-453`) | да | пробелы |
| `continue` (`StmtContinue`, `ast.go:57`) | потерь нет: вид различает `continue`, `Range` покрывает `continue` и `;` (`parse.go:449-453`) | да | пробелы |

| `decl` (`StmtDecl`, `ast.go:61`) | слова типа потребляются `parseLocalDecl` и в AST не сохраняются — у `Stmt` нет поля типа (`parse.go:813`, `ast.go:823-832`), при этом `Range.Start` покрывает область типа (`parse.go:810`); каждый декларатор — `ExprIdent` или бинарный `=` с дублированием имени (`parse.go:826`, `parse.go:833-836`) | имена и значения — да, тип — нет | слова типа, `,`, `;`, пробелы; имя не печатать дважды |

| `action` (`StmtAction`, `ast.go:65`) | аналогично `condition`: `kind=StmtAction` (`parse.go:788-790`), `:` и `{`-форма не различимы, тело только при `{` (`parse.go:792-802`) | ключевое слово и тело при `{` — да, форма — нет | `action`, `:`/`{`, `}`, пробелы |

Сквозное по `Stmt`:

- `expectSemi` удлиняет `Range.End` обычных стейтментов до конца `;`
  (`parse.go:1251-1262`); у составных форм (`if`/`while`/`for`/`switch`/`case`/
  `condition`/`action`) `Range.End` = конец вложенного стейтмента, и
  разделитель как таковой в узле не представлен.

### Expr — 6 видов

| вид | что теряется | годится ли для дословной печати | что принтеру синтезировать |
|-----|--------------|---------------------------------|----------------------------|
| `call` (`ExprCall`, `ast.go:71`) | при постфиксном `(` операнд-калибл заменяется узлом call: если калибл не голый идентификатор, он теряется — `a.b(x)` даёт `Callee=""`, `Children=[x]`, приёмник `a.b` в узле отсутствует (`parse.go:952-955`); `Range.End` — конец последнего аргумента, `)` вызова вне `Range` (`parse.go:948-950`), при пустом списке `Range` = только имя калибла; `Callee` — строка из `identName` (`parse.go:1293-1299`) | аргументы и простое имя — да; сложный калибл — нет | `(`, `,`, `)`; приёмник при калибле-не-идентификаторе |
| `binary` (`ExprBinary`, `ast.go:73`) | `Value` — текст оператора; для `.` и `[]` значения синтетические (`[]` таким текстом в исходнике не встречается) (`parse.go:965-968`, `parse.go:979-982`); у `a[b]` `Range` покрывает `a[b`, `]` вне него (`parse.go:969-982`); при неудаче правого операнда возвращается `lhs`, и оператор из узла пропадает (`parse.go:895-898`); скобки группировки не сохраняются — `parseParenExpr` возвращает внутреннее выражение без покрытия скобок (`parse.go:1034-1038`) | обычная бинарная операция — да; `.`/`[]` и группировка — нет | `[`, `]`, скобки группировки по приоритетам, пробелы вокруг оператора |
| `unary` (`ExprUnary`, `ast.go:75`) | постфиксные `++`/`--` хранятся со `Value` = `"++post"`/`"--post"` — синтетическим написанием, которого в исходнике нет (`parse.go:983-988`); `Value` смешивает префиксную и постфиксную формы; при неудаче разбора операнда `Range` = только токен оператора, операнд отсутствует (`parse.go:921`) | префиксные — да; постфиксные — по отображению `post`-суффикса | `x++`/`x--` из `post`-суффикса, пробелы |
| `literal` (`ExprLiteral`, `ast.go:77`) | числовое `Value` — дословный текст токена, включая `0x`/`0X` и ведущие нули (`parse.go:1002`, `scanNumber` `parse.go:1553-1577`); строковое `Value` включает окружающие кавычки (`scanString` `parse.go:1580-1608`, токен `parse.go:1487-1492`); голый блок `{...}` становится литералом `"{}"` с `Range` только по `{`, тело блока пропускается целиком (`parse.go:1011-1015`) | числа и строки — да (текст строкового значения уже содержит кавычки); голый блок — нет | кавычки строки как часть значения; тело блока из AST не восстановимо |
| `vector` (`ExprVector`, `ast.go:79`) | строится только при ровно трёх компонентах (`parse.go:1052-1057`), `Range` покрывает `(`..`)` (`parse.go:1055`); при числе компонент ≠ 3 — предупреждение и возврат только первого операнда, остальные отбрасываются (`parse.go:1059-1062`) | при трёх компонентах — да; иначе — нет | для ≠3 — ничего (лишние операнды в AST отсутствуют) |
| `ident` (`ExprIdent`, `ast.go:81`) | `Value` и `Range` — токен целиком (`parse.go:1006`); идентификатор после `.` синтетический: `Value` = текст члена, `Range` = его токен, `p.record` для члена не вызывается (`parse.go:956-968`) | да | пробелы |

Сквозное по `Expr`:

- тернарный оператор: `?` и `:` входят в `singleOps` (`parse.go:1393`), но
  `binaryPrec` их не знает (`parse.go:1323-1350`) — узел для `a ? b : c` не
  создаётся, оба оператора в AST отсутствуют;
- `parseBinary` при неудаче правого операнда возвращает `lhs`
  (`parse.go:895-898`) — хвостовой оператор (`a +`) в узел не попадает.

Сквозное по лексеру:

- сканер собирает два независимых потока: `comments` — экстенты строчных и
  блочных комментариев (`parse.go:1463`, `parse.go:1470`), и `strings` —
  экстенты строковых литералов (`parse.go:1490`); строковые токены отделены
  от комментариев, чтобы потребитель их не путал; тексты не хранятся,
  читаются по `Offset` источника.
- сознательное изменение поведения (не «тишина не изменилась»): фикс
  исчисления координаты `Start` многострочных токенов (снятие `startPos` до
  потребления токена, `parse.go:1454-1457`) ИСПРАВИЛ «тишину»
  `CallAt`/`VisibleAt` внутри многострочных блочных комментариев и строк с
  экранированным переводом строки — раньше `Start.Column` уходил в underflow
  `uint32`, и `Contains` не срабатывал никогда; существующий
  `TestCallAt_InBlockComment` этого не ловил (проба стоит до вызова).
