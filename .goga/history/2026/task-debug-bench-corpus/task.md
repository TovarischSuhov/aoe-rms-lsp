# Отладочные логи, бенчмарки и корпус-прогон 100 опубликованных карт

## Current State

- `cmd/aoe2-lsp/main.go` ставит `slog` TextHandler на stderr с уровнем по
  умолчанию (Info). Способа включить debug-уровень из редактора нет: ни
  флага, ни env. Точек debug-логирования внутри ячеек практически нет —
  только `WarnContext` при ошибке publishDiagnostics в `internal/server`
  и логи генерации в `internal/kb`.
- Бенчмарков в репозитории нет ни одного (`func Benchmark` отсутствует во
  всех пакетах). Производительность и аллокации горячих путей (parse,
  analysis, completion, hints, include-closure) не измерены; CLAUDE.md
  требует «сделал быстрее» подтверждать benchstat'ом, но базы для
  сравнения нет.
- Все фикстуры рукописные и маленькие (`internal/rms/testdata` — 7
  файлов, `internal/xs/testdata` — 5). Полный пайплайн (parse →
  diagnostics → outline → hover/completion) на реальных опубликованных
  картах не прогонялся; устойчивость к боевому контенту (CRLF, BOM,
  экзотические секции, include-цепочки, гигантские файлы) не проверена.

## Description

Три связанных, но независимо поставляемых направления усиления
эксплуатационной готовности aoe2-lsp:

1. **Отладочные логи.** Флаг `-debug` у `aoe2-lsp`: slog-уровень Debug на
   stderr (stdout остаётся под протокол). Достаточный набор debug-событий
   жизненного цикла и запросов в `internal/server` (initialize,
   didOpen/didChange, публикация диагностики, вход/выход хендлеров), чтобы
   «разборки» по инцидентам были возможны без пересборки.
2. **Бенчмарки и слабые места.** `Benchmark*` для горячих путей каждой
   ячейки (`rms.Parse`, `xs.Parse`, `analysis`, `hints`, `complete`,
   `include.Closure`, `kb.NewStore`) с `-benchmem`; профилирование pprof;
   отчёт со слабыми местами (аллокации, подозрение на квадратичность) в
   `docs/`. Точечные исправления очевидных узких мест — в объёме,
   не требующем правки контрактов.
3. **Корпус-прогон реальных карт.** Детерминированный сэмпл из 100
   опубликованных RMS-скриптов (публичные GitHub-коллекции), прогон
   in-process полного пайплайна над каждым файлом, детект паник,
   зависаний и ошибок. Найденные проблемы фиксируются в этом плане и
   исправляются (фиксы — атомарными коммитами/PR по ячейкам).

## Scope

**In scope:**

- Флаг `-debug` в `cmd/aoe2-lsp`; настройка уровня до старта Serve.
- Debug-события в `internal/server` (lifecycle + запросы; без полезной
  нагрузки документов — только мета: uri, версия, длины, количества).
- Бенчмарки в ячейках rms/xs/analysis/hints/complete/include/kb на
  детерминированных входах (существующие testdata + генерируемые большие
  входы); сценарий запуска и отчёт `docs/reviews/` со слабыми местами.
- Corpus-харнесс: тонкий entrypoint + логика в подходящей ячейке,
  скрипт загрузки сэмплa (список URL с фиксацией SHA/коммита источника,
  seeded random 100 из пула), прогон под cgroup-песочницей, отчёт.
- Исправления багов и паник, найденных корпусом; крэш-фиксы приоритетнее
  оптимизаций.

**Out of scope:**

- Новые зависимости (`go get`) — всё на stdlib.
- Правка контрактов `CODEMANIFEST` ячеек (read-only в кодовых задачах);
  если без правки API нельзя — пункт в план, не в код.
- Коммит загруженных скриптов в репозиторий (лицензии) — только список
  источников и скрипт загрузки.
- Крупные рефакторинги производительности, меняющие публичную
  поверхность ячеек.
- Трассировка таймингов каждого запроса в production-режиме (это debug).

## Acceptance Criteria

- `aoe2-lsp -debug` пишет debug-события на stderr; без флага — уровень
  Info, stdout не содержит логов (протокол чист) — проверено тестом.
- В каждой ячейке с горячим путём есть `Benchmark*`, запускаемые `go
  test -bench`; отчёт со слабыми местами и числами (benchstat-совместимый
  формат) лежит в `docs/reviews/`.
- Команда корпуса скачивает пул и прогоняет ровно 100 карт за разумное
  время под memory-cap песочницей; прогон завершается без паник — либо
  каждая найденная проблема закрыта фиксом или явно записана в план.
- Все найденные на корпусе баги имеют воспроизводимые тесты (фикстуры из
  фрагментов реальных скриптов, без копирайт-объёмных вставок).
- `make check` зелёный; `goga contract` затронутых ячеек зелёный.

## Stack

- **Frameworks:** Go 1.26 stdlib: `log/slog`, `flag`, `testing`
  (benchmarks), `runtime/pprof`.
- **Libraries:** существующие (jsonrpc2/protocol для харнесса, если он
  пойдёт через server-ячейку; testify в тестах).
- **Infrastructure:** GitHub raw как источник корпуса (curl в скрипте
  загрузки), cgroup-песочница для прогонов (`systemd-run`, memory
  `go-tests-under-memory-cap`).

## Risks and Constraints

- Реальные скрипты: CRLF/BOM/8-bit кодировки, include-циклы, очень
  большие файлы — парсер обязан не падать (это и проверяем).
- Публичные коллекции могут двигаться/пропадать — фиксируем коммит SHA
  источников в списке; загрузка идемпотентна с кэшем.
- Случайность сэмпла должна быть воспроизводимой — фиксируем seed и
  полный получившийся список.
- Тесты и бенчмарки — только под memory cap; corpus-прогон тоже.
- Найденные баги могут расползаться по нескольким ячейкам — фиксы
  отдельными атомарными коммитами; при необходимости отдельные PR.
- Бенчмарки не должны стать хрупкими: входы генерируются
  детерминированно, без сети в `go test`.

## Scope Estimate

Разбивка на 3 независимо поставляемые подзадачи (по PR):

1. **PR A — debug-логи**: флаг `-debug`, slog-уровень, debug-события в
   `internal/server`, тест (флаг/уровень, stdout чист). Малый объём.
2. **PR B — корпус-прогон**: харнесс + скрипт загрузки + список 100 карт,
   прогон, отчёт, фиксы найденных багов (крэши/паники — обязательно;
   ложные срабатывания диагностики — по результатам). Фиксы — атомарные
   коммиты внутри PR, межъячеечные — при необходимости отдельные PR.
3. **PR C — бенчмарки**: `Benchmark*` по ячейкам, генерируемые входы,
   отчёт со слабыми местами, точечные оптимизации без правки контрактов.

Рекомендуемый порядок: A → B → C (корпус даёт реалистичные данные для
отчёта производительности и приоритизации).

## Existing Architecture

- `cmd/aoe2-lsp` — тонкий entrypoint; server ячейка (`internal/server`)
  уже принимает зависимости через конструктор и берёт логгер из
  `slog.Default()` + `protocol.WithLogger` — флаг реализуется без правки
  API ячеек.
- Corpus-харнесс: входная точка — тонкий `cmd/`-entrypoint; логика
  прогона над файлом — потребитель ячеек rms/analysis/hints/complete
  (вероятная домашняя ячейка — `internal/server`, уже владеющая
  docstore'ом и диспетчеризацией). Точное распределение — предмет
  brainstorm.
- CODEMANIFEST всех ячеек — read-only.
