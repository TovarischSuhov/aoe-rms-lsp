# Best practices реализации в реальных RMS/XS картах

Справочник практик **внутри карт** — что и как пишут авторы работающих
карт, что движок молча игнорирует, какие приёмы стоят за самыми
играемыми картами. Собран по корпусу из 263 опубликованных скриптов
(прогон 09.09.2026) и гайду Зетнуса; компаньон
[real-map-nuances.md](real-map-nuances.md) (полный список отклонений от
документации). Пригодится для кураторства kb, правил линтера и новых
карт.

## RMS

### 1. Вариантная карта — одна if/elseif-мегачепочка

Турнирная серия WSVG ([KHR_WSVG](https://github.com/HSZemi/rms/tree/c422ed5e4eda735bd5ef705bd409ecb446c1502d/STANDARD_MAPS_WITH_USER_PATCH_FEATURES/KOTH_REGICIDE/WSVG%20Single%20Maps%20v2))
делает так: в шапке `start_random/percent_chance` выбирает `#define`
варианта, затем одна гигантская `if WSVG_ACROPOLIS … elseif … endif`
обёртывает ВСЕ секции карты — каждый вариант это по сути целая карта в
ветке. Работает (движок не требует закрывать условия до конца файла),
но:

- парить такой файл редактором без LSP больно — endif за 2500 строк от if;
- копипаста вариантов порождает опечатки, которые никто не замечает
  (см. п. 5).

Для новых карт предпочтительнее: один вариант = один файл + `#include`.

### 2. Общие атрибуты после условной цепочки

Паттерн es@-карт: несколько `create_terrain <имя>` в ветках, а ОБЩИЙ
`{ … }`-блок атрибутов открывается после `endif` — движок привязывает
его к последней create_-команде. Экономит дублирование, но хрупко:
порядок веток меняет получателя атрибутов. Для читаемости лучше явный
блок в каждой ветке или `#include` общего фрагмента.

### 3. Скобки `{ }` вокруг атрибутов — опциональны, но пишите их

Движок принимает `create_object TUNA` + атрибуты строками ниже +
завершающий `}` (5 карт корпуса так написаны). Атрибуты после команды
прикрепляются позиционно до следующей команды/условия/секции. Без
скобок легко «прикрепить» атрибут не туда при рефакторинге — всегда
пиши `{ … }`.

### 4. `#include` — основной инструмент переиспользования

`#include Team_Islands_lands.rms` — общие фрагменты (lands, ресурсы)
выносятся в подключаемые файлы. В corpus-пуле целые семейства карт так
устроены. Путь — относительный к файлу с директивой; движок DE
проверяет существование файла (missing include = ошибка генерации).
Наш анализатор помечает отсутствующие include как `missing-include`.

### 5. Не переносите атрибуты между create_-командами

Главный источник «мёртвых» директив в реальных картах: авторы копируют
`border_fuzziness` с create_land на create_terrain, `set_scale_by_size`
с terrain на create_object. Движок **молча игнорирует** неизвестные
атрибуты — карта работает, эффект пропадает незамеченным. В корпусе
таких ~145 использований, включая турнирные карты, играемые годами
(полная таблица — [real-map-nuances.md](real-map-nuances.md), раздел 3).
Перед использованием атрибута сверяйтесь с секцией нужной команды в
гайде.

### 6. Комментарии: три ловушки

- **Самореферентный текст**: комментарий, объясняющий синтаксис
  комментариев, содержит `*/` — и закрывает сам себя
  ([first_map.rms](https://github.com/Maboey/aoe2_rms/blob/3f064dbeedbdd4a490d974ae1c0cf7b5bc44353b/first_map.rms)):
  после него французский текст стал «командами».
- Кавычки внутри `/* … */` безопасны (движок их не трактует как строки).
- Не-ASCII (CP1251/UTF-8, диакритика) в комментариях и даже в словах —
  терпится движком.

### 7. Легаси `#include_drs` — можно не выпиливать

45% корпуса (включая официальные карты DE `real_world_*`) несут
`#include_drs random_map.def 54000` — наследие AoC/HD. В DE это no-op:
оставлять безвредно, новые карты — не писать.

### 8. `effect_percent` → `effect_amount`

Deprecated с DE; в корпусе 36 использований в 3 картах. Новые карты —
только `effect_amount`.

### 9. `#const`/`#define` в шапке — конвенция корпуса

Практически каждая большая карта начинает с блока `#const NAME id`
(`#const ROCKS 40`). Держите их в одном месте в шапке — так проще
находить и переиспользовать.

## XS

Идиомы из реальных библиотек
([aoe2de_xslibs](https://github.com/mardaravicius/aoe2de_xslibs),
[aoe2-xs-comm](https://github.com/qferre/aoe2-xs-comm)):

1. **Модульные константы через `extern const`**: `extern const int
   cIntListSuccess = 0;` — префикс модуля + camelCase, статус-коды как
   отрицательные константы, sentinel вроде `-999999999` для «пустого
   параметра».
2. **Дефолтные параметры** (`int xsIntListCreate(int capacity = 7)`) —
   рабочий механизм XS; имитация перегрузок через 12 optional-параметров
   + sentinel (см. `xsIntList`).
3. **Динамические структуры поверх `xsArray*`**: списки/словари
   строятся на `xsArrayCreateInt/SetInt` с счётчиком длины в нулевой
   ячейке.
4. **Приватность конвенцией**: `_cIntListIntMax`, `_intListLast…` —
   подчёркивание = внутреннее состояние модуля; настоящего private нет.
5. **Документирующие блоки `/* … */` с `@param/@return`** перед
   функциями — как в xslibs; наш hover их не показывает (только сигнатуру
   из kb) — авторская документация остаётся в коде.
6. **`const int` локалы** внутри функций — встречаются в реальном коде;
   поддержка движком не подтверждена (см. nuances), для надёжности
   выносите в верхний уровень.
7. **Чего в XS нет** (проверено кейсами UGC Guide): `long`, `double`,
   `char`, `goto` — не работают, не использовать.
8. `prelude.xs` (дамп встроенной библиотеки, `docs/ref/ugc-guide/xs/`) —
   канонический список встроенных функций/констант: 884 extern-декларации.

## Общее

- **Тестируйте в игре, а не «компилируется же»**: движок RMS глотает
  неизвестные имена молча — единственный способ поймать мёртвую
  директиву это видеть эффект генерации. LSP-сервер этого репозитория
  подсвечивает их как `unknown-attribute`/`unknown-command`.
- Мёртвый код не падает — поэтому выживает годами: в турнирных картах
  по 50+ молча игнорируемых строк. Ревью карт линтером (наш
  `analysis`) перед публикацией — дешёвая страховка.
